## 1. The five things that will actually bite us

Ranked by how likely they are to cause a silent, hard-to-debug failure. Read this section even if you read nothing else.

### 1.1 Unmanaged attributes are **disabled by default** — custom attributes are invisible AND unwritable, with no error

**[docs]** <https://www.keycloak.org/docs/latest/server_admin/index.html#_understanding-managed-and-unmanaged-attributes>

> By default, Keycloak will only recognize the attributes defined in your user profile configuration. **The server ignores any other attribute not explicitly defined there.**

> Although unmanaged attributes are disabled by default, you can configure your realm using different policies […] click on the `Realm Settings` at the left side menu, click on the `General` tab, and then choose any of the following options from the `Unmanaged Attributes` setting:
>
> - **Disabled** — "This is the default policy so that unmanaged attributes are disabled from all user profile contexts."
> - **Enabled** — "This policy enables unmanaged attributes to all user profile contexts."
> - **Admin can view** (`ADMIN_VIEW`) — "This policy enables unmanaged attributes only from the administrative context as read-only."
> - **Admin can edit** (`ADMIN_EDIT`) — "This policy enables unmanaged attributes only from the administrative context for reads and writes."

JSON enum values: `DISABLED` / `ENABLED` / `ADMIN_VIEW` / `ADMIN_EDIT` (`UPConfig.unmanagedAttributePolicy`).

**"Administrative context" includes the Admin REST API.** **[code]** `UserProfileContext.USER_API(true, …)` — the first constructor flag is the admin-context flag. So our `client_credentials`-authenticated `GET`/`PUT /admin/realms/{realm}/users/{id}` is governed by this policy.

Failure mode under the default `Disabled`:

- **Read** — the attribute is simply **absent from the JSON**. No error, no warning. **[code]** `DefaultUserProfile.toRepresentation` builds the map from `attributes.getReadable()`.
- **Write** — the attribute is **silently discarded**. HTTP 204, nothing persisted.
- **Fast diagnosis** — **[docs]** "When unmanaged attributes are enabled (even if partially) you can manage them from the administration console at the **Attributes** tab in the User Details UI. **If the policy is set to Disabled this tab is not available.**" Open any user in the admin console; no Attributes tab ⇒ policy is `Disabled`.

**Recommended fix — declare the attribute as _managed_, don't flip the realm to `Enabled`.** Realm settings → User profile → JSON editor:

```json
{
  "name": "enrollment_year",
  "displayName": "Enrollment Year",
  "permissions": { "view": ["admin"], "edit": ["admin"] },
  "validations": { "pattern": { "pattern": "^[0-9]{3,4}$" } },
  "annotations": { "inputType": "text" }
}
```

**[docs]** rules: `view`/`edit` accept `"user"` / `"admin"`; **"When the `edit` permission is granted, the `view` permission is implicitly granted."** The docs argue against the blanket switch: _"try to adhere to the most strict policy as much as possible […] Avoid setting the `Enabled` policy […] The `Enabled` policy is targeted for realms migrating from previous versions."_ The threat-model chapter adds: _"Administrators should not allow unmanaged attributes for users to prevent attackers adding an unlimited number of attributes."_

Managed via API at `GET`/`PUT /admin/realms/{realm}/users/profile`.

### 1.2 `PUT /users/{id}` is a **full replace** — a naive single-attribute write destroys the others

**[docs]** Upgrading guide, _Migrating to 24.0.4_:

> When updating user attributes through the Admin User API, you cannot execute partial updates […] if you are updating user attributes through the Admin User API **without passing all the attributes that the administrator has write permissions, the missing attributes will be removed.** On the other hand, if an attribute is marked as read-only for administrators, not sending the attribute won't remove it.

Every writer must GET → merge in memory → PUT. Our existing `updateKeycloakProfile()` in `apps/portal/lib/profile/keycloak.ts` already does this and documents why — **keep that invariant in anything new.**

### 1.3 Since **26.3.0**, user _search_ respects the user profile too

**[docs]** Upgrading guide, _Migrating to 26.3.0_:

> When querying users through the User API, the user representation and their attributes are now taking into account the user profile settings defined for the realm. **It might happen that attributes in user representations are no longer available depending on the user profile configuration where too much information was returned in the past.**

Before 26.3 the list endpoint leaked attributes regardless of profile config. Any code or tutorial that "worked" on an older Keycloak may break here. This is the single most likely explanation if a previously-working attribute read starts returning nothing.

### 1.4 `q=` searching vs returning is **asymmetric**

**[code]** `JpaUserProvider.predicates()` builds the `q` predicate straight against the `USER_ATTRIBUTE` table with no user-profile consultation. So under `Disabled`, a search **still matches** on an unmanaged attribute while the returned representation **omits** it. Filtering appears to work; the value comes back missing. Not documented — verify against our realm before relying on it either way.

### 1.5 Attribute-name search became **case-sensitive** in 25.0.0

**[docs]** Upgrading guide, _Migrating to 25.0.0_ — "Removing custom user attribute indexes":

> When searching for users by user attribute, Keycloak no longer searches for user attribute names forcing lower case comparisons. This means Keycloak's native index on the user attribute table will now be used.

Attribute **names** must match stored case exactly; **values** are still compared lower-cased. Normalize on write, and never read an empty search result as "the user has no such attribute".

## 2. Least-privilege access model

### 2.1 `realm-management` client roles

**[docs]** <https://www.keycloak.org/docs/latest/server_admin/index.html#_per_realm_admin_permissions>

> Each realm has a built-in client called `realm-management`. […] This client defines client-level roles that specify permissions that can be granted to manage the realm.

Roles relevant to user work, verbatim from the FGAP "Roles and Permission relationship" table:

| Role           | **[docs]** description                                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `query-users`  | "…can see the _Users_ section in administration console and can search for users in the realm. **It does not grant the ability to _view_ users.**"                |
| `view-users`   | "A realm administrator can _view_ all users and groups in the realm."                                                                                             |
| `manage-users` | "A realm administrator can _view_, _map-roles_, _manage-group-membership_ and _manage_ all users in the realm…"                                                   |
| `realm-admin`  | the realm-scoped superuser. **[code]** a composite of **every** other `realm-management` role (`RealmManager.setupRealmAdminManagement()`). **Never grant this.** |

**[code]** composites: `view-users` → `query-users` + `query-groups`. `manage-users` is _not_ a composite of `view-users`, but `canView()` returns true for `MANAGE_USERS`, so `manage-users` subsumes read.

**Minimum role per operation** **[code]**, from `UserPermissions` / `UsersResource` / `UserResource`:

| Operation                        | Endpoint                                           | Minimum role                |
| -------------------------------- | -------------------------------------------------- | --------------------------- |
| Read one user (incl. attributes) | `GET /admin/realms/{realm}/users/{id}`             | **`view-users`**            |
| List / search users              | `GET /admin/realms/{realm}/users`, `…/users/count` | **`view-users`** — see trap |
| Update a user                    | `PUT /admin/realms/{realm}/users/{id}`             | **`manage-users`**          |

> **Trap.** `query-users` alone passes `requireQuery()` (HTTP **200**) but `UsersResource.toRepresentation()` then applies `.filter(usersEvaluator::canView)`, so the caller gets an **empty array, not a 403**. `query-users` exists to render the console's Users menu, not to return data. Grant `view-users`.

**[docs]** `manage-users` cannot self-escalate: _"Admins with the `manage-users` role will only be able to assign admin roles to users that they themselves have."_

### 2.2 Realm-scoped service account, never master

**[docs]** <https://www.keycloak.org/docs/latest/server_admin/index.html#_understanding_different_types_realm_admins_>

> - **Server administrators**: […] granted with the `admin` role in the master realm.
> - **Realm administrators**: […] granted with the `realm-admin` role in a specific realm.
> - **Delegated realm administrators**: […] granted access through the fine-grained admin permissions feature.
>
> The main difference between them is that **server administrators can manage any realm in the server, while realm administrators can only manage the realm they have been granted access to.**

On a shared Keycloak, a service account living **inside** the target realm is structurally incapable of reaching another realm — `realm-management` is per-realm. It also means creating it needs only that realm's admin rights, not master credentials.

### 2.3 Fine-Grained Admin Permissions (FGAP v2) — GA, but mutually exclusive with `view-users`

**[docs]** <https://www.keycloak.org/server/features> lists `admin-fine-grained-authz:v2` under **Supported features … enabled by default**. Not preview; there is no flag to turn on (v1 is deprecated, `--features=admin-fine-grained-authz:v1`). Per-realm activation: **Realm settings → Admin Permissions** toggle.

The decisive constraint **[docs]**:

> Fine grained permissions are used to grant **additional** permissions. You **cannot override the default behavior of the built-in admin roles**. […] if a respective admin role is assigned to a realm administrator, **permission evaluation will be bypassed, and access will be granted.**

So it is one model or the other:

- **Model A (simple, realm-wide)** — grant `view-users` / `manage-users`. FGAP is bypassed.
- **Model B (true least privilege)** — grant **only `query-users`**, enable _Admin Permissions_, and create a Users permission with scope `view` (later `manage`) bound to a `User` policy naming `service-account-<clientId>` or a `Group` policy. Also lets you grant attribute writes **without** `reset-password` (separate scope since 26.4.0).

Model B costs documented per-request overhead and a lot of setup. **Model A is the recommendation for winlab** unless the realm operator wants otherwise.

## 3. Admin console setup (26.7.0 labels)

**[docs]** create client — `proc-creating-oidc-client.adoc`:

> 1. Click _Clients_ in the menu. 2. Click _Create client_. 3. Leave _Client type_ set to _OpenID Connect_. 4. Enter a _Client ID._ 5. Supply a _Name_. 6. Click _Save_.

**[docs]** Capability config — `con-basic-settings.adoc`:

> **Client authentication** — _ON_ … **Clients with the client authentication enabled are referred as confidential clients.**
> **Service account roles** — "If enabled, this client can authenticate to Keycloak and retrieve access token dedicated to this client. In terms of OAuth2 specification, this enables support of `Client Credentials Grant` for this client."

For a machine credential: Client authentication **On**; Authorization **Off**; Standard flow / Direct access grants / Implicit **Off**; **Service accounts roles On**.

> Label spelling differs between doc files ("Service account roles" vs "Service accounts roles"); the shipped i18n bundle has `serviceAccount=Service account roles`.

**[docs]** `proc-using-a-service-account.adoc`, steps that are easy to miss:

> Click the _Client Scopes_ tab, select the dedicated client scope […] Verify that you have roles or toggle _Full Scope Allowed_ to _ON_. **Note that this switch is useful only for the development purposes and in the production, it is recommended to disable this switch and properly configure role scopes.**
>
> Click the _Service Account Roles_ tab of your client. Configure the roles available to this service account.

> **[unconfirmed]** The literal button labels _Assign role_ and the _Filter by clients_ dropdown on that tab are not in the written docs (the guide uses a screenshot). Operationally: **Assign role** → switch the filter to **Filter by clients** → search `realm-management` → tick the role.

The service-account principal is a real user named **`service-account-<CLIENT_ID>`** — that's what an FGAP `User` policy would reference.

⚠️ **26.7.0 change [docs]:** "Service accounts excluded from user queries by ID … If you need to access a service account, use the dedicated client service account endpoints" (`GET /admin/realms/{realm}/clients/{uuid}/service-account-user`).

### Client authentication method

**[docs]** Credentials tab → _Client Authenticator_: **Client Id and Secret** (`client-secret`, default) · **Signed JWT** (`client-jwt`, "enables the client to authenticate without a shared secret") · **Signed JWT with Client Secret** (`client-secret-jwt`) · **X509 Certificate** (`client-x509`) · **Signed JWT issued by an Identity Provider** (`client-federated-jwt`, supported since 26.6, covers Kubernetes service accounts).

**[code]** The built-in `oauth-2-1-for-confidential-client` global profile allows only `client-jwt` and `client-x509`, defaulting to `client-jwt` — Keycloak's own OAuth 2.1 profile excludes shared secrets. That is the strongest documented production signal.

Honest assessment for our case: Signed JWT protects against _transit / log / server-DB_ exposure and enables rotation via **Use JWKS URL**, but the private key still sits on the same disk the secret would — against "attacker has filesystem read", it is not meaningfully better. A client secret in Vercel's secret store is defensible for the app; the laptop credential's real defence is being scoped to `view-users`.

⚠️ **26.2.0 [docs]:** Signed JWT now enforces a **max expiration, default 60 s** — mint assertions immediately before use, never cache them.
⚠️ **26.7.0 [docs]:** newly generated client secrets are **86 characters** ("to provide enough entropy for HS512"). Check any length limits in secret stores.

**Client secret rotation is a _preview_ feature** (`--features=client-secret-rotation`), implemented as a `secret-rotation` client-policy executor, and **[docs]** _"Rotations do not occur automatically or through a background process"_ — you must call Regenerate Secret. Not a turnkey answer; Signed JWT + JWKS URL is the better rotation story.

## 4. API cheat sheet for our use case

Token — **[docs]** `proc-using-a-service-account.adoc`:

> The REST URL to invoke is `/realms/{realm-name}/protocol/openid-connect/token`. This URL must be invoked as a **POST** request […] By default, client credentials are represented by the clientId and clientSecret of the client in the _Authorization: Basic_ header […] You also need to set the _grant_type_ parameter to `"client_credentials"`.

> Instead of using the header `Authorization: Basic`, it is also possible to send the credentials as parameters `client_id` and `client_secret` of the POST request.

**No refresh token, and that's correct** **[docs]**: _"Only the access token is returned by default. No refresh token is returned and no user session is created […] Due to the lack of a refresh token, re-authentication is required when the access token expires."_ The _Use refresh tokens for client credentials grant_ switch (Advanced → OIDC Compatibility Modes) exists but should stay **off** — it creates a session per grab and RFC 6749 §4.4.3 says it SHOULD NOT be issued.

**[code]** `Constants.DEFAULT_ACCESS_TOKEN_LIFESPAN = 300` (5 min); overridable per realm (_Realm settings → Tokens_) and per client (_Advanced → Access Token Lifespan_). **Read `expires_in` from the response rather than hardcoding**, cache in-process with a margin, and re-fetch on expiry.

`GET /admin/realms/{realm}/users` params **[docs, from the OpenAPI spec]**:

| Param                                                                                                                                        | Notes                                                                                                                                                                                                                                                                  |
| -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `briefRepresentation`                                                                                                                        | "Boolean which defines whether brief representations are returned **(default: false)**" — ⇒ **`attributes` ARE returned by default** on this endpoint. Do not pass `true`. (Contrast: `/organizations/{id}/members` defaults to brief since 26.1.0. Don't generalize.) |
| `q`                                                                                                                                          | "A query to search for custom attributes, in the format 'key1:value2 key2:value2'". Space-separated pairs, AND-ed. Double-quote values containing spaces.                                                                                                              |
| `exact`                                                                                                                                      | **[code]** for custom attributes via `q`, matching is **exact by default** (`getOrDefault(EXACT, "true")`) — the inverse of `username`/`email`. `exact=false` switches `q` to `LIKE '%…%'` **and** loosens the name/email params in the same request.                  |
| `first` / `max`                                                                                                                              | offset / "Maximum results size (defaults to 100)". **[code]** no server-side hard cap. No cursor, no total header — pair with `/users/count`, stop when a page returns `< max`.                                                                                        |
| `search`, `username`, `email`, `firstName`, `lastName`, `enabled`, `emailVerified`, `idpAlias`, `idpUserId`, `createdBefore`, `createdAfter` | standard filters                                                                                                                                                                                                                                                       |

Documented existence query **[docs]**, _Migrating to 26.4.0_:

> `GET /admin/realms/{realm}/users?exact=false&q=myattribute:`

`GET /admin/realms/{realm}/users/{id}` — only param is `userProfileMetadata`; always full. Representation:

```json
{
  "id": "…",
  "username": "…",
  "email": "…",
  "enabled": true,
  "attributes": { "enrollment_year": ["113"] }
}
```

**Every attribute value is an array of strings** — read as `attributes?.[key]?.[0]`. **[docs]** since 24.0.0 the map holds **only custom attributes**: _"you should not expect any root attribute in the map"_ — `username`/`email`/`firstName`/`lastName` are top-level fields.

⚠️ **26.6.3 [docs]:** user profile metadata is no longer returned on user _search_ (performance); fetch a single user with `?userProfileMetadata=true` if needed. `attributes` is unaffected.

Server-wide read-only attributes, denied even to admins **[docs]**: `KERBEROS_PRINCIPAL`, `LDAP_ID`, `LDAP_ENTRY_DN`, `CREATED_TIMESTAMP`, `createTimestamp`, `modifyTimestamp`. Unmanaged attribute values cap at **2048 characters**.

**Rate limiting: none documented for the Admin API.** The only server-side throttle is `http-max-queued-requests` (**[docs]** default: no limit), which returns **503 Server not Available** — there is no 429 and no `Retry-After`. Self-throttle (bounded concurrency) and treat 503 as the overload signal.

Admin REST base path is `/admin/realms/…` — **no `/auth` prefix** since Keycloak 17. Ignore older examples.

⚠️ Admin API **v2** (`--features=client-admin-api:v2`, new in 26.7.0) is **[docs]** _"experimental […] Do not use this feature in production"_ and covers **clients only, not users**. Irrelevant here.

## 6. Decisions for the winlab realm

**Provisioned on 2026-08-05** by `kc bootstrap --apply`; see §7 for what was
measured afterwards. Recorded here so later work doesn't re-litigate them.

1. **Two clients, split by blast radius.**
   - `winlab-portal-admin` — `manage-users`. Secret in Vercel (prod) and in `apps/portal/.env.local` when developing `/profile` locally. This is what `KEYCLOAK_ADMIN_CLIENT_ID` / `_SECRET` already refer to.
   - `winlab-kc-cli` — **`view-users` only**. The credential this machine and any coding agent uses. Read-only by construction, so a leaked laptop secret cannot mutate the realm; revoking it cannot take prod down.
2. **Model A** (`realm-management` roles), not FGAP — the realm is small and FGAP would be bypassed by `view-users` anyway.
3. **Client secret**, not Signed JWT, for now — Vercel holds a string well, and the laptop credential's protection is its scope. Revisit if the realm operator adopts the OAuth 2.1 profile.
4. **Any new attribute is declared as _managed_** with `permissions.view/edit = ["admin"]`, rather than flipping the realm's Unmanaged Attributes policy. (The enrollment year needed no such change — `admissionYear` was already declared; see §7.)
5. **Full Scope Allowed OFF** on both clients' dedicated scope; **Use refresh tokens for client credentials grant** OFF.
6. Never `realm-admin`; never a master-realm credential.

## 7. Realm snapshot — measured 2026-08-05

**This section is a dated measurement, not live state.** Counts and rosters
change with every intake. Nothing downstream should copy these numbers; run the
commands instead — they are the source of truth:

```bash
bun run kc doctor --attr admissionYear   # the gate, roles, and a live read
bun run kc profile                       # declared attributes + admin access
bun run kc users --attr admissionYear    # distribution and coverage
```

Taken at `https://auth.winlab.tw`, realm `winlab`, with the read-only `cli`
credential.

- [x] **Unmanaged Attributes = `DISABLED`** — Keycloak's default, so §1.1 applies
      in full: anything not declared below is invisible to the Admin API.
- [x] **12 attributes are declared** (managed), all `admin: read+write`:
      `username`, `email`, `firstName`, `lastName`, `chinese_name`,
      **`admissionYear`**, `username_email`, `role`, `phone`, `student_id`,
      `position`, `gitlabUsername`.
- [x] **The enrollment year is `admissionYear`** — 民國學年, three digits
      (`107`–`115`). Not 西元. Already managed and admin-readable, so **no realm
      change is needed to read it**.
- [x] **Coverage is partial: 47 of 260 users have a value, 213 do not.**
      Distribution: 107×1, 108×1, 110×4, 111×5, 112×8, 113×10, 114×10, 115×8.
      Consequence for the presenter pool: `admissionYear` **cannot be the sole
      source of pool membership** — an admin still curates the roster, and the
      UI must allow setting the year by hand when Keycloak has none.
- [x] **Both service-account clients exist and their tokens carry the expected
      roles** — `winlab-kc-cli` → `view-users` (plus the `query-users` /
      `query-groups` composites), `winlab-portal-admin` → `manage-users`.
- [x] `view-users` is **sufficient to read `/users/profile`** — the tool's
      earlier assumption that this needed a broader role was wrong.

Still open:

- [ ] Whether `KEYCLOAK_*` env vars are set in the **portal's hosting
      environment** — provisioning cannot reach outside Keycloak. PR #326
      shipped without a verified live integration.
- [ ] **[unconfirmed]** claim 1.4 (search matches unmanaged attributes but does
      not return them) — untested; nothing depends on it yet.
- [ ] The realm's **deployed Keycloak version**. `/admin/serverinfo` is
      restricted to master-realm admins in 26.7.0, so the service accounts
      cannot read it. Behaviour observed so far is consistent with 26.x.

### Trap this cost us once

`fullScopeAllowed: false` is the documented production setting, but with it off
a token's roles are the **intersection** of the service account's roles and the
client's **scope mappings**. Granting the role to the service account alone
produces a client that Keycloak's console shows as correctly configured while
every admin call 403s. Both halves are required:

```
POST /admin/realms/{realm}/users/{sa-user-id}/role-mappings/clients/{realm-mgmt-uuid}
POST /admin/realms/{realm}/clients/{client-uuid}/scope-mappings/clients/{realm-mgmt-uuid}
```

`kc bootstrap` now does both and then authenticates as the new client to read
the roles back — a `204` from either call proves nothing on its own.
